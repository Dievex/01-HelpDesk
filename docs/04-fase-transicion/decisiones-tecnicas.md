# Decisiones Técnicas por Iteración

Registro de las decisiones tomadas en cada iteración de Transición, con su motivo — mismo criterio que el documento homónimo de [Construcción](../03-fase-construccion/decisiones-tecnicas.md).

## Iteración 1 — Empaquetado de producción

- **`docker-compose.prod.yml` como archivo aparte de `docker-compose.yml`**, no un `override`/profile del mismo archivo — las diferencias son estructurales (target de imagen, qué puertos se publican, servicio de reverse proxy nuevo), no solo unos pocos valores; mezclar todo en un único archivo con profiles hubiera sido más difícil de leer que dos archivos completos y explícitos.
- **`db` y `app` no publican puertos al host en producción** (sí lo hacen en `docker-compose.yml` de dev, para poder pegarle a la API o a Postgres directo durante el desarrollo). En producción, `app` solo es alcanzable a través de `caddy`, y `db` no necesita ser alcanzable desde fuera de la red de Docker Compose en ningún caso — reduce la superficie de ataque.
- **Nuevo target `migrate` en el `Dockerfile`** (`FROM base`, con la CLI de Prisma disponible) y servicio `migrate` en el compose de producción, que corre `prisma migrate deploy` y sale. Necesario porque el target `prod` deliberadamente no trae la CLI de Prisma (es `devDependency`, omitida con `--omit=dev` — decisión de la Iteración 0 de Construcción) y `migrate deploy` no se puede correr ahí. `app` depende de que `migrate` termine con éxito (`condition: service_completed_successfully`) antes de arrancar.
- **`prisma/seed.js` no se automatiza como servicio del compose.** A diferencia de las migraciones, sembrar el catálogo base y el Administrador inicial es una acción de una sola vez que además imprime la contraseña del Administrador en el log (ver Iteración 0 de Construcción) — se deja como paso manual documentado en el manual de instalación (Iteración 2), no como algo que corra solo cada `docker compose up`.
- **Caddy como reverse proxy, no Nginx + Certbot.** Emite y renueva el certificado HTTPS de Let's Encrypt solo, sin un `cron` ni contenedor aparte de Certbot ni configuración manual de renovación — para un despliegue self-hosted de un único administrador, la config de una línea (`{$DOMAIN} { reverse_proxy app:3000 }`) pesa más que el ecosistema más grande de Nginx.
- **El dominio (`DOMAIN`) se pasa por variable de entorno al `Caddyfile`**, no queda hardcodeado — mismo criterio que el resto de "configuración de instancia, no valor fijo del producto" ya usado en `arquitectura.md`/Construcción (p. ej. `REOPEN_GRACE_DAYS`).
- **No se tocó código de `server/`** para esta iteración: el flag `secure` de la cookie de sesión ya dependía solo de `NODE_ENV === 'production'` (Iteración 1 de Construcción), no de `req.secure`/cabeceras del proxy, así que funciona sin cambios detrás de Caddy. Tampoco hay ninguna lógica que lea `req.ip`/`req.protocol` que necesitara `app.set('trust proxy', ...)`.
- **`.env.prod.example` separado de `.env.example`** (que sigue siendo el de desarrollo) — mismas claves, pero con los valores inseguros de desarrollo (`changeme`, `admin123`) vacíos y marcados como obligatorios de generar, más la clave nueva `DOMAIN` que no existe en desarrollo.

**Cierre:** `docker compose -f docker-compose.prod.yml config` valida sin errores de sintaxis/interpolación con un `.env` de prueba. Build real de los 4 targets del `Dockerfile` (`dev`, `build`, `migrate`, `prod`) verificado con `docker build --target <nombre>`. Falta la validación end-to-end completa (levantar la pila entera y probar la app real detrás de Caddy) — se hace en la Iteración 2 junto con el manual, porque requiere un dominio real con DNS apuntando a la máquina de prueba para que el HTTPS automático funcione.

## Iteración 2 — Manual de instalación + validación end-to-end + cierre de fase (PRM)

- **Validación end-to-end aislada del entorno de desarrollo activo**: la pila de producción se levantó con `docker compose -p helpdesk-prod-check` (nombre de proyecto propio, volúmenes propios: `helpdesk-prod-check_db-data`, etc.), en paralelo al `01-helpdesk-app-1`/`01-helpdesk-db-1` de desarrollo que seguían corriendo — sin pisarlos ni tocar su `.env`. Se confirmó al final que el stack de dev seguía respondiendo (`http://localhost:5173` → 200) sin haber sido afectado.
- **Gotcha real encontrado al validar, documentado para no repetirlo**: `env_file: - .env` en `migrate`/`app` lee el archivo `.env` **real** del proyecto, no el que se pasa con `docker compose --env-file <otro>` (ese flag solo controla la interpolación `${VAR}` del propio YAML, no lo que carga `env_file:`). En un despliegue real no es un problema porque solo existe un `.env` (el que el manual pide crear desde `.env.prod.example`), pero para probar con credenciales de prueba sin tocar el `.env` de dev hizo falta un compose override que fija `environment:` explícito en `migrate`/`app` (`environment` tiene prioridad sobre `env_file` por clave) — override que vivió fuera del repo, no se commiteó nada de la prueba en sí.
- **HTTPS validado con el modo `tls internal` de Caddy, no con un certificado real de Let's Encrypt.** La máquina de desarrollo no tiene DNS público apuntándole ni los puertos 80/443 abiertos a internet, así que el challenge ACME real no es reproducible acá. Se probó en cambio el mismo `Caddyfile` de producción con `tls internal` agregado temporalmente (revertido con `git checkout` apenas terminó la prueba, nunca commiteado) — valida el mismo mecanismo de terminación TLS + reverse proxy, solo cambia quién firma el certificado. La emisión real contra Let's Encrypt queda como riesgo residual, documentado en el manual, a validar en el primer despliegue real con dominio público.
- **El seed (`node prisma/seed.js`) corre sin problema dentro del contenedor `prod`** aunque ese target no tenga la CLI de Prisma — el script usa `@prisma/client` directo (ya copiado desde el stage `build`), no el comando `prisma db seed`. Confirmado ejecutándolo de verdad contra la base de datos limpia del stack de prueba.
- **`docker compose down -v` limpia volúmenes y `docker image rm` las imágenes de prueba** después de validar — no queda nada del stack de `helpdesk-prod-check` en el Docker del usuario.

**Cierre (PRM):** stack completo (`migrate` → `db` → `app` → `caddy`) levantado desde cero, migraciones aplicadas contra una base vacía, seed ejecutado, login real vía `POST /api/auth/login` a través de HTTPS (Caddy con `tls internal`) devolviendo la cookie `token` con `HttpOnly`/`Secure`/`SameSite=Lax`, una llamada autenticada a `GET /api/usuarios` respondiendo con los datos reales, la misma ruta sin cookie respondiendo 401, el cliente estático (`index.html` del build de Vite) servido en la raíz, y la redirección automática `http://` → `https://` de Caddy confirmada con código 308. Manual de instalación (`manual-instalacion.md`) escrito con los pasos realmente probados, incluyendo backup/restauración de los volúmenes `db-data`/`uploads` y el procedimiento de actualización. Único punto fuera de alcance de esta validación: la emisión real de un certificado de Let's Encrypt contra un dominio público (requiere infraestructura que no existe en la máquina de desarrollo) — queda documentado como el primer paso a confirmar en el despliegue real.
