# Decisiones Técnicas por Iteración

Registro de las decisiones de implementación tomadas en cada iteración de Construcción, con su motivo — mismo criterio que las iteraciones de Elaboración en el [Plan de Desarrollo de Software](../01-fase-inicio/plan-desarrollo-software.md), pero como artefacto propio de esta fase. El código lleva como mucho un comentario corto señalando que la decisión está aquí; el razonamiento completo vive en este documento, no en el código.

## Iteración 0 — Entorno y esqueleto

- **Jerarquía de rol (`Usuario ← AgenteSoporte ← Supervisor`, `Usuario ← Administrador`) resuelta como tabla única `Usuario`** con enum `rol` y campos nullable `nivel`/`equipoId`, en vez de una tabla por subtipo. Evita repartir las FK de `Ticket.solicitanteId`/`agenteId` entre varias tablas para un caso de uso que siempre trata "quien reporta" y "quien atiende" como el mismo concepto.
- **IDs como UUID**, no autoincrementales — portabilidad entre entornos (2 PCs) sin depender de secuencias que puedan desincronizarse.
- **`SLA.tiempoPrimeraRespuesta`/`tiempoResolucion` en minutos.** El Modelo de Dominio no fijaba la unidad; se decide aquí.
- **`Notificacion.leida` (booleano) añadido sin equivalente en el Modelo de Dominio.** Necesario para la decisión de Iteración 3 de entregar `Notificacion` como lista in-app.
- **Modo de desarrollo: todo dentro de Docker**, con bind-mount de código para hot-reload — decidido con el usuario para no depender de tener Node nativo con la misma versión en las 2 PCs.
- **Estructura de carpetas por vertical slice** (`server/src/modules/<controller>/`), no por capa técnica — 1 carpeta = 1 de los 8 Controllers que ya define el Modelo de Análisis/Diseño.
- **npm workspaces** (`client`, `server`) con un único `package-lock.json` — un solo `npm install` al cambiar de PC.
- **La base de datos se trata como reproducible, nunca se porta el volumen de datos a mano**: migraciones Prisma + `prisma/seed.js` en git, volúmenes de Docker con nombre (no bind-mounts a rutas del host).
- **Prisma 7 evaluado y descartado.** Elimina `datasource.url` en el schema (exige `prisma.config.ts` + adapters), incompatible con "JavaScript, no TypeScript" de la [Decisión de Arquitectura](../02-fase-elaboracion/arquitectura.md). Se mantiene Prisma 5.x.
- **Vite, Vitest y react-router-dom actualizados a su última major** (nada dependía aún de las APIs viejas) — 0 vulnerabilidades en `npm audit`.

**Bugs de infraestructura encontrados y resueltos:**
- Faltaba `.dockerignore` — el contexto de build incluía `node_modules` y `.git` (257MB).
- Prisma necesita OpenSSL, que Alpine no trae por defecto (`apk add openssl`).
- El `postinstall: prisma generate` necesita `prisma/schema.prisma` copiado *antes* del `npm ci` en la imagen, si no el layer de dependencias no lo encuentra.
- El stage `prod` no puede regenerar el cliente Prisma (la CLI es `devDependency`, omitida con `--omit=dev`) — copia el cliente ya generado desde el stage `build`.

**Cierre:** `docker compose up --build` probado desde cero (`down -v` + rebuild) simulando un checkout limpio en la segunda PC — migración y seed funcionando, target `prod` también construido y probado end-to-end.

## Iteración 1 — Acceso y Sesión + Usuario

- **El Administrador fija la contraseña inicial directamente** al crear un Usuario — no hay flujo de recuperación por correo (self-hosted, sin SMTP decidido en la Decisión de Arquitectura).
- **JWT con payload mínimo `{sub, rol}`**, cookie `httpOnly`/`sameSite=lax`/`secure` solo en producción, expira a las 8h. Limitación conocida (ya en el Patrón 01 de Elaboración): sin revocación server-side — si el rol de un Usuario cambia, sus sesiones activas conservan el rol viejo hasta volver a iniciar sesión.
- **`equipoId` de Usuario no se expone todavía** (ni en el formulario ni en la API) — `Equipo` no tiene CRUD hasta la Iteración 2.
- **UC-40 Eliminar Usuario: la validación de bloqueo por tickets asociados está escrita y activa**, pero no se puede demostrar todavía porque `Ticket` no tiene datos reales hasta la Iteración 3.
- **Confirmación de borrado con `window.confirm()` nativo**, no un modal propio — simplificación deliberada de esta iteración.
- **UC-37 Ver Usuario se implementó como el mismo formulario de edición, precargado** — no una pantalla de solo lectura aparte, mismo criterio que el resto del CRUD de configuración (Patrón 06: "EntityForm sirve para Crear y Editar").

**Bugs de infraestructura encontrados y resueltos:**
- `node --watch` no detecta cambios de forma fiable a través del bind-mount de Docker en Windows — cambiado a `nodemon --legacy-watch` (polling) en el server, y `usePolling: true` en Vite para el cliente.
- El volumen con nombre de `node_modules` no se refresca solo al reconstruir la imagen tras añadir una dependencia nueva — hay que borrarlo a mano (`docker volume rm 01-helpdesk_app-node-modules`) cuando pase. Documentado también como comentario corto en `docker-compose.yml`.

**Cierre:** probado en navegador real (no solo por API): login con el admin seedeado y con un usuario recién creado, guardia de rol en frontend y backend, CRUD completo de Usuario (crear con campo "Nivel" condicional, ver/editar precargado, eliminar con confirmación).

## Iteración 2 — Catálogo: Categoría, Equipo, Prioridad+SLA

- **`onDelete: SetNull` añadido explícitamente en `Usuario.equipo` y `Categoria.equipo`** — resultó ser ya el comportamiento por defecto de Prisma en relaciones opcionales (no generó migración), pero se deja explícito en el schema porque documenta la intención ("Eliminar Equipo no bloquea, cascada a sin equipo") sin tener que ir a buscar la regla en la documentación de Prisma.
- **`SLA` se crea/edita anidado dentro de `Prioridad`** (`sla: { create/update: {...} }` de Prisma), sin ruta ni Controller propios — coherente con la decisión ya tomada en Elaboración de que `SLA` no tiene CRUD propio.
- **Sin componente compartido de lista/formulario entre Categoría, Equipo y Prioridad**, aunque el Patrón 06 los modela como un único `EntityForm`/`EntityListView` genérico. Los tres campos que varían (Categoría con selector de Equipo, Prioridad con los dos campos de SLA, Equipo sin nada extra) hacían que una abstracción genérica necesitara props de configuración por campo — más indirección que las ~60 líneas que cuesta repetir cada página. Revisar si vale la pena extraerla si aparece una quinta entidad con la misma forma.
- **`equipoId` de Usuario completado** (pendiente desde la Iteración 1): selector condicional a rol Agente/Supervisor, igual criterio que el campo Nivel.
- **UC-25/UC-35 (bloqueo de borrado de Categoría/Prioridad en uso): validación escrita y activa**, mismo caso que UC-40 en la Iteración 1 — no demostrable hasta que `Ticket` tenga datos reales (Iteración 3).
- **Seed extendido con catálogo base** (Equipo "Soporte General", Categoría "General", Prioridad "Media" con SLA 60/480 min) usando `upsert` idempotente, para no depender de crear todo a mano antes de poder probar un Ticket en la Iteración 3.

**Cierre:** probado en navegador real: CRUD completo de las 3 entidades, selector de Equipo en Categoría y en Usuario, SLA precargado al editar una Prioridad, y el caso de borrado en cascada verificado visualmente — al eliminar un Equipo en uso, la Categoría y el Usuario que lo referenciaban pasan a mostrar "—"/"Sin equipo" sin error.

## Iteración 3 — Ticket, flujo mínimo viable

- **FA-1 de UC-11 (condición de carrera al tomar un ticket) resuelta con un guard atómico en el `where` de `updateMany`** (`agenteId: null, estado: 'ABIERTO'|'ESCALADO'`), no con un check-then-act en dos pasos — dos agentes tomando el mismo ticket a la vez no pueden pisarse: como mucho uno de los dos `updateMany` afecta una fila.
- **Control de acceso a UC-04 Ver Ticket resuelto releyendo el `Usuario` completo desde la base de datos**, no confiando en el `{sub, rol}` del JWT — el `equipoId` (necesario para decidir si un Agente/Supervisor tiene acceso por pertenecer al Equipo de la Categoría) puede haber cambiado después de que se emitió el token, y el JWT ya no se revoca ni se refresca (limitación de la Iteración 1).
- **`Notificacion` se crea en base de datos (Supervisor al crear, Solicitante al resolver) pero no tiene pantalla propia** — el catálogo de 43 casos de uso nunca incluyó un "Ver Notificaciones" a propósito ("recibir una notificación no es un objetivo que el actor persigue activamente"). Construir una bandeja ahora sería alcance no pedido por ningún UC; se deja como fila en la tabla, lista para cuando (si) se decida exponerla.
- **Seed de Prioridad extendido a Baja/Media/Alta** (antes solo tenía Media) — "Baja" es obligatoria: UC-03 crea todo ticket nuevo con esa Prioridad por defecto, y si no existe, la creación de tickets falla con un 500 explícito en vez de silencioso.
- **Plazo de Reapertura configurable vía `REOPEN_GRACE_DAYS`** (por defecto 7 días), convertido a minutos en `config/env.js` — mismo criterio que el resto de "configuración de instancia, no valor fijo del producto" (arquitectura.md).
- **El Administrador puede crear tickets pero no tomarlos/resolverlos/ver la cola** — no hereda de `AgenteSoporte` en el Modelo de Casos de Uso, solo de `Solicitante`. Las rutas `/tomar`, `/resolver` y `/cola` están protegidas con `requireRole('AGENTE', 'SUPERVISOR')`.

**Cierre:** probado en navegador real de punta a punta con dos usuarios distintos: Administrador crea un ticket → Agente lo ve en su Cola ("Sin asignar") → lo toma con un clic (estado pasa a Asignado) → lo resuelve con comentario (estado pasa a Resuelto, comentario y los 3 eventos de auditoría CREACION/ASIGNACION/RESOLUCION visibles en el historial). Verificado además que un Solicitante puro no puede abrir el ticket de otro actor (403, sin revelar datos) ni acceder a `/cola` por URL directa (redirige a inicio).

## Iteración 4 — Ticket, resto del ciclo de vida

- **Bug real encontrado y corregido: `GET /api/categorias` y `GET /api/prioridades` estaban completamente cerrados a Administrador** (heredado tal cual de la Iteración 2, pensado solo para el CRUD de configuración). Rompía UC-03 Crear Ticket para cualquier no-administrador (el selector de Categoría no cargaba) y UC-41 Priorizar Ticket para el Supervisor (no podía leer el catálogo de Prioridades). Se separó lectura (abierta a cualquier autenticado) de escritura (sigue exclusiva de Administrador) en ambos routers. No se detectó en la Iteración 3 porque todas las pruebas de creación de tickets se hicieron con la cuenta de Administrador.
- **Nuevo endpoint `GET /api/usuarios/mi-equipo`**, fuera del guard de Administrador — UC-18/UC-19 exigen que el Supervisor vea los Agentes de su propio Equipo para asignar/reasignar, sin darle acceso al CRUD completo de Usuario.
- **El motivo de Escalar (UC-13) y Reabrir (UC-08) se guarda como `Comentario`, no como campo nuevo en `EventoAuditoria`.** Elaboración nunca resolvió dónde vive ese texto (`EventoAuditoria` solo tiene `tipoEvento`/`fecha`, no un campo libre). Se reutiliza el mismo mecanismo que ya usa el comentario opcional de UC-12 Resolver, en vez de añadir una columna nueva — visible en la misma sección "Comentarios" del detalle, con autor y fecha.
- **`Reabierto → EnProgreso` no tiene caso de uso propio (Diagrama de Estados), así que `resolver()` acepta también el estado `REABIERTO` directamente** — mismo criterio que `tomar()` ya usaba para asumir `Escalado → EnProgreso` sin un paso intermedio. `escalar()`, en cambio, sigue restringido a `Asignado`/`EnProgreso` tal como fija literalmente la precondición de UC-13 (un ticket reabierto no se puede volver a escalar sin pasar antes por resolverlo).
- **Asignar y Reasignar comparten el mismo guard atómico contra condiciones de carrera que Tomar** (`updateMany` con el estado/agente esperado en el `where`), extendido en Reasignar a los tres estados de UC-19 (`Asignado`, `EnProgreso`, `Reabierto`).
- **Cierre automático como `node-cron` dentro del proceso Express** (`server/src/jobs/cierreAutomatico.js`), cada 5 minutos por defecto (`CIERRE_AUTOMATICO_CRON`), sin servicio nuevo — tal como fijó el roadmap de Construcción. Reutiliza el mismo `EventoAuditoria` tipo "Cierre" que Confirmar Cierre, pero con `autorId = null` (el Sistema, no un actor).

**Cierre:** las 9 transiciones probadas en navegador real con 3 usuarios (Administrador como Solicitante, Sara como Supervisora, Alex como Agente): escalar (libera el agente, notifica a Sara), Sara asigna el ticket escalado a Alex, Sara confirma la Prioridad (y un segundo intento de priorizar el mismo ticket es rechazado con 409), Alex resuelve, el Solicitante reabre con motivo, Alex resuelve de nuevo (confirmando que `Reabierto` es resoluble sin paso intermedio) y el Solicitante confirma el cierre — historial final `CREACION → ASIGNACION → RESOLUCION → REAPERTURA → RESOLUCION → CIERRE`. Cierre automático verificado por separado: se forzó el vencimiento de `fechaLimiteReapertura` de un ticket `Resuelto` y se confirmó en base de datos que quedó `Cerrado` con un `EventoAuditoria` de tipo "Cierre" y `autorId` nulo.

## Iteración 5 — Contenido de Ticket + Base de Conocimiento

- **`Adjunto` gana `nombreFisico`** (nueva migración), separado de `nombreArchivo` (el original, para mostrar) — el nombre físico en el volumen es un UUID + extensión, para no depender de sanitizar nombres de archivo arbitrarios ni arriesgar colisiones.
- **Adjuntos con `multer` + `diskStorage`**, guardando directo en `UPLOADS_DIR` (por defecto `/app/uploads`, mismo volumen con nombre `uploads` ya declarado en `docker-compose.yml` desde la Iteración 0). Lista blanca de tipos por `ADJUNTO_TIPOS_PERMITIDOS` y tamaño máximo por `ADJUNTO_TAMANO_MAX_MB`, ambas configurables por instancia (mismo criterio que el Plazo de Reapertura). El error de tamaño excedido de multer se traduce a `AppError` en `middleware/upload.js` porque multer lo lanza fuera del `fileFilter`.
- **Descarga de adjuntos con el mismo control de acceso que Ver Ticket** (`GET /:id/adjuntos/:adjuntoId`), sirviendo el archivo con su nombre original vía `res.download()`.
- **Base de Conocimiento: lectura (`GET /api/articulos`) abierta a cualquier autenticado**, con el filtro Público/Interno por rol resuelto en el servicio — mismo patrón ya corregido en categorías/prioridades durante la Iteración 4. Escritura (crear/editar/eliminar) exclusiva de Agente de Soporte/Supervisor; Administrador no hereda de `AgenteSoporte`, así que no puede escribir en la Base de Conocimiento aunque sí pueda leerla.
- **Un único componente de frontend (`ArticuloFormPage`) sirve tanto UC-09 Ver como UC-16 Editar**, decidiendo en tiempo de render si el actor tiene permiso de escritura: si no, muestra solo título/contenido/visibilidad de lectura; si sí, el formulario completo con Guardar/Eliminar. Evita duplicar la pantalla de detalle para dos casos de uso que comparten toda la carga de datos.
- **Búsqueda de artículos con `contains`/`insensitive` de Prisma** (ILIKE de Postgres) sobre título y contenido — confirma la decisión ya tomada en Elaboración de no introducir un motor de búsqueda de texto completo.

**Cierre:** probado en navegador real con 2 usuarios (Pepe como Solicitante puro, Alex como Agente): Pepe solo ve el artículo Público en el listado y en la búsqueda, y el acceso directo por URL al Interno da 403 sin revelar contenido; Pepe comenta y sube un adjunto real desde el input de archivo del navegador, ambos visibles de inmediato en el detalle; Alex crea un artículo nuevo (aterriza en el detalle ya editable, con Guardar/Eliminar). Vinculación probada por API: Alex vincula el artículo público al ticket de Pepe (aparece en "Artículos vinculados" y en el historial como VINCULACION), un segundo intento de vincular el mismo artículo es rechazado con 409 (FA-2). Persistencia de adjuntos verificada de verdad: se reinició el contenedor `app` y el adjunto subido antes seguía descargable con el mismo contenido, confirmando que el volumen con nombre `uploads` sobrevive al ciclo de vida del contenedor.

## Iteración 6 — Dashboard de Métricas

- **Módulo `reports` sin modelo propio** — a diferencia del resto de módulos (`server/src/modules/<entidad>/`), este es puramente de lectura/cálculo sobre `Ticket`, `Comentario` y `Prioridad.sla` ya existentes, tal como fija el Patrón 07. Un único endpoint, `GET /api/reports/metricas?desde&hasta`, exclusivo de Supervisor.
- **"Primera respuesta de Agente de Soporte" incluye comentarios de Supervisor**, no solo de rol `AGENTE` — mismo criterio que `ROLES_CON_EQUIPO` ya usado en `tickets.service.js`: `Supervisor` hereda de `AgenteSoporte` en el Modelo de Dominio, así que su comentario también cuenta como respuesta del equipo.
- **El rango de fechas se recibe como `YYYY-MM-DD` y se expande en el servidor** a `T00:00:00.000`/`T23:59:59.999` para que "hasta" incluya todo lo creado ese último día, no solo hasta medianoche. La validación de FA-2 (`desde` posterior a `hasta`) vive en el servicio (400) y además se bloquea en el cliente con los atributos `min`/`max` nativos de `<input type="date">`, para feedback inmediato sin redondtrip.
- **Tickets sin dato aportan `null` a un promedio/porcentaje, no cero ni "no cumplido"** — un ticket `Resuelto` sin comentario de Agente queda fuera del cálculo de primera respuesta (ni sube ni baja el promedio ni el cumplimiento), tal como fija la regla de negocio de UC-20. Se implementa filtrando `null` antes de promediar/contar, en vez de tratarlo como incumplimiento.
- **Sin almacenamiento del resultado de cumplimiento de SLA** — se recalcula en cada consulta comparando en vivo contra `Prioridad.sla` del ticket, cerrando **R-07** definitivamente (ya no quedaba pendiente ninguna decisión de estructura, solo esta lógica).
- **Frontend con `<input type="date">` nativo**, sin librería de selector de fechas — mismo criterio de "sin dependencias nuevas si el navegador ya lo resuelve" del resto del proyecto. Rango por defecto: día 1 del mes actual hasta hoy.

**Cierre:** probado en navegador real como Sara (Supervisora) con datos creados vía API: 3 tickets del Equipo "Soporte General" en el rango — uno `Resuelto` con comentario previo de Alex (Agente) antes de resolver, uno `Resuelto` sin comentario previo, uno `Abierto` sin tocar. Volumen mostró total 3 (1 Abierto, 2 Resuelto); tiempos y cumplimiento de SLA calculados correctamente, con el ticket sin comentario excluido del promedio y del cumplimiento de primera respuesta (no contó como incumplimiento). FA-2 verificada: el campo "Desde" posterior a "Hasta" queda inválido por el `max` del input y el formulario no llega a enviarse. FA-1 verificada: un rango sin tickets (enero 2026) muestra el aviso "No hay tickets creados en el rango seleccionado." sin error.

## Cierre de fase / hardening — Pruebas automatizadas del backend (retroactivas)

Hasta la Iteración 5 el cierre de cada iteración se verificó solo a mano (navegador real + API) — decisión consciente para no frenar el ritmo de construcción, dejada explícitamente pendiente de decidir antes de declarar IOCM (ver roadmap). Se decidió con el usuario escribirlas ahora, retroactivas a las 6 iteraciones, en vez de darlas por cubiertas solo con la verificación manual ya hecha.

- **Base de datos de test propia (`helpdesk_test`), misma instancia de Postgres que la de desarrollo (`db`), nunca la de desarrollo/demo.** Se crea y migra sola (`server/tests/globalSetup.js`, `CREATE DATABASE` vía un `PrismaClient` apuntando a la URL base + `prisma migrate deploy`) para que `npm run test --workspace=server` funcione con el `docker compose up` ya levantado, sin ningún paso manual previo — mismo criterio de reproducibilidad que el resto del proyecto (Iteración 0).
- **`DATABASE_URL` se reescribe en `server/tests/setup.js`** (derivando `helpdesk_test` de la URL real por regex, sin archivo `.env.test` nuevo) **antes de que cualquier módulo de la app importe `prisma.js`** — Vitest garantiza que los `setupFiles` corren antes que el archivo de test, así el `PrismaClient` singleton se construye ya apuntando a la base de test.
- **Aislamiento entre tests con `TRUNCATE ... RESTART IDENTITY CASCADE`** antes de cada test (no solo por archivo) sobre las 11 tablas del esquema — más simple y explícito que envolver cada test en una transacción revertida, y suficientemente rápido para el tamaño de la suite (46 tests, ~16s). `fileParallelism: false` en `vitest.config.js` porque todos los archivos comparten la misma base de datos.
- **Alcance: integración vía Supertest contra la app real (`createApp()`), no unitarios con mocks de Prisma** — coherente con que el mayor riesgo ya identificado en el proyecto son las reglas de negocio (guards de condición de carrera, control de acceso por rol/equipo/pertenencia), no la lógica aislada de una función. `server/tests/helpers.js` centraliza los fixtures (crear usuario con contraseña hasheada, login que devuelve un agente de Supertest con la cookie de sesión ya guardada, escenario base Equipo+Categoría+Prioridad "Baja").
- **Se priorizó cubrir las reglas de negocio ya señaladas como no obvias en este mismo documento**, no ir por cobertura exhaustiva de cada rama de cada caso de uso: el guard atómico de condición de carrera al Tomar un ticket (dos agentes a la vez, con `Promise.all`, verificando que solo uno de los dos `updateMany` afecta una fila), el control de acceso por Equipo en Asignar/Reasignar/Priorizar, el bloqueo de borrado de Usuario/Categoría/Prioridad en uso, la cascada `SetNull` de Equipo, la exclusión de tickets sin comentario de Agente del cálculo de primera respuesta del Dashboard, y el cierre automático por vencimiento con `autorId` nulo.
- **Bug real encontrado por la propia suite y corregido:** `res.clearCookie` en `auth.controller.js` pasaba `maxAge` (deprecado en Express, ignorado a partir de v5) — se corrigió excluyendo `maxAge` de las opciones antes de llamarlo, ya no emite el warning.
- **Fuera de alcance de esta pasada:** tests de frontend. `client/package.json` ya tiene Vitest + React Testing Library instalados desde la Iteración 0 pero sin usar — se deja pendiente, no se decidió explícitamente escribirlos ahora.

**Cierre:** `docker compose exec app npm run test --workspace=server` — 8 archivos, 46 tests, todos en verde, corriendo contra el entorno Docker ya levantado sin ningún paso de setup manual adicional.
